# 黄金集（Golden Set）

## 现状

| 文件 | 状态 | case 数 |
|---|---|---|
| `video.yaml` | ✅ 完整样例，可直接作为模板 | 7 |
| `legal.yaml` | ⬜ 待 S0 语料采集后补齐 | 0 |
| `support.yaml` | ⬜ 待 S0 语料采集后补齐 | 0 |

三份 YAML 的 `eval.golden_set` 都已指向对应路径，补齐后 S3 才能跑全量评测。

## 数据从哪来（优先级从高到低）

1. **历史返修单 / 退回记录**（最优）——真实发生过的问题，天然带"为什么不行"的理由。样例里 `V-002` 的标题直接就是返修单编号 `R-104`。
2. **专家现场造的边界 case**——专家说"这种情况我肯定打回"，当场录一条。
3. **线上 `fail` + 人工 `reject` 回流**（S6 起）——真实运行的失败样本自动进候选池，需人工确认后才入集。

**不要**用模型生成 case。生成出来的 case 会天然贴合模型自己的偏好，测不出真实缺陷。

## 每条 case 的必备字段

| 字段 | 作用 |
|---|---|
| `case_id` | 稳定标识，`行业前缀-序号`，入集后不可改 |
| `title` | 一句话说明这条 case 考什么，最好带返修单号 |
| `inputs` | 运行输入参数，必须能让 pack 真实跑起来 |
| `artifact` | 产物样本路径（`fixtures/` 下），真实文件而非描述 |
| `expect` | 断言列表：**必须命中的判据及其状态** |
| `tags` | 分类标签，用于分组跑与失败定位 |

## `expect` 的断言原则

1. **只断言有把握的判据**。没列出的判据不参与断言，只统计——否则一处无关改动会让整套集红掉。
2. **一条 case 至少 2 条断言**，且尽量跨槽位（一条 quality + 一条 veto 更有效）。
3. **必须包含"应当通过"的 case**（如 `V-001`）。只有失败样本的黄金集会奖励"过度严格的判据"。
4. **`status: skipped` 也是一条有效断言**——它验证 `applies_when` 条件写对了（如 `V-005` 验证披露缺失时不应走到人工签署）。

## 覆盖率要求（S3 Gate）

- 每条 `severity: block|veto` 的判据，至少被 1 条 case 命中 `fail`。
- 每条 `judge` 类判据，至少 2 条 case（一条高分一条低分），否则无法校准 `pass_if` 阈值。
- 报告里必须显示**判据覆盖率**：`被命中判据数 / 总判据数`。低于 70% 不允许发布。

## 扩充节奏

- S3：每包 ≥ 10 条
- S4：压测期间不动黄金集（避免"改测试让它过"）
- S6：线上回流每两周入库一批，人工确认后合并
