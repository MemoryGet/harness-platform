# 收入模型与定价（三条腿的定位）

> 本文回答一个问题：这套东西靠什么挣钱，三条收入腿各自站在什么位置，以及为什么它们不能平等对待。
> 关联：`01-roadmap.md`（阶段与 Gate）、`05-decisions.md`（D-012）、`06-knowledge.md`（判据资产的数据模型）。

---

## 1. 三条腿的时间性完全不同

不能把"服务 / 网关 / 判据库"当成三个并列的生意。它们在四个维度上的性格差异极大：

| | 对接服务 | token / 模型通道 | 判据库订阅 |
|---|---|---|---|
| 首笔收入 | 1–3 个月 | 1 个月 | 9–18 个月 |
| 毛利率 | 40–60%（卖人力） | 5–15%（卖差价） | 80%+（卖软件） |
| 可规模化 | 差（线性绑人） | 好（但价格被上游压） | 好 |
| 是否沉淀资产 | **会**，但必须强制 | 否，只沉淀用量数据 | **是，且复利** |
| 主要风险 | 退化成外包公司 | 毛利被模型降价吃掉 | 周期长，需前两条养着 |
| 战略角色 | **现金流引擎** | **计量入口** | **资产与终局** |

正确的关系是：**服务养活团队，网关提供计量点，判据库承接复利**。顺序不能反——先做判据库会饿死，只做服务会永远停在人力生意。

---

## 2. 对接服务：现金流引擎，但必须设"资产化"硬规则

### 2.1 定位

卖的不是"帮你搭 agent"，是**帮一个团队把他们的判据变成可验收的交付流程**。这话术的差别很实际：前者客户拿 Dify 免费版跟你比价，后者客户在买"我们公司的规矩被固化下来"。

### 2.2 报价结构（建议）

| 项 | 内容 | 参考价 |
|---|---|---|
| 诊断 | 2–3 天访谈，输出判据草案（10–20 条） | 1–3 万，可抵扣后续 |
| 实施 | 1 个业务包上线 + 1 套 golden set + 培训 | 3–8 万 |
| 陪跑 | 每月 2 次判据修订 + 月报 | 0.5–1.5 万/月 |
| 私有化 | 内网部署 + 数据不出域 | 加 30–50% |

### 2.3 硬规则：每单必须沉淀判据资产

**没有这条规则，服务收入永远换不来护城河。** 具体做法：

1. 每单交付必须产出至少 1 份可复用的判据模板（脱敏后进模板库）；
2. 服务工时的 **20–30% 记账为"资产投入"**，在内部损益里不算成本——否则你永远会觉得"做模板不挣钱"，然后停止做；
3. 合同里写明：判据模板的**方法论与结构**归你，**具体业务规则与数据**归客户。这条要提前谈，事后补会被视为侵占。

### 2.4 退出条件（提前定，否则会一直做下去）

当出现以下任一信号，服务收入占比必须主动下调：

- 同一类需求第 3 次出现，且已有模板可套 → 转成标准包的订阅；
- 单个客户月度工时超过 5 天 → 说明包不成熟或在做定制开发，要么涨价要么拒单；
- 销售线索里超过一半问"能不能便宜点" → 客户群错位，你在卖人力而不是卖判据。

## 3. token / 模型通道：通道可以留，利润中心不要做

### 3.1 为什么不建议靠差价挣钱

三条结构性理由，都不是执行问题：

1. **上游随时压价。** 模型单价过去两年持续大幅下降，你的收入基数在缩水，而成本端（算力）没有同等降幅。转售的毛利是"时间函数"，只会变薄。
2. **客户可以直连。** 网关这层已被彻底商品化：LiteLLM 月下载量数亿级、OpenRouter 以聚合模式跑通且盈利，都是免费或薄利。你加价的空间天然被钉住。
3. **责任不会因为转售而转移。** 面向境内提供生成式服务涉及备案与内容安全责任，转售不构成免责；一旦上游变更条款或区域策略，你的交付直接断供。

### 3.2 但它有一个别人拿不走的价值：计量点

网关是**唯一能同时看到"谁在用、用了多少、用在哪一步"的位置**。这正是判据业务需要的东西——第 5 节会用到。

所以正确的定位是：**网关不赚差价，赚"验收 + 计量 + 对账"的服务费。**

| 做法 | 收什么 | 毛利 |
|---|---|---|
| ❌ 转售 token | token 差价 | 5–15%，逐年下降 |
| ✅ 网关托管 | 按"通过验收的交付次数"收服务费；token 按成本价透传（甚至公开成本单） | 60%+ |
| ✅ 私有化网关 | 一次性部署费 + 年维护 | 70%+ |

透传成本还有个额外好处：**客户不会怀疑你为了多卖 token 而放松判据**。这一点在下一节是致命的。

## 4. 判据库：卖订阅，不卖库

### 4.1 为什么不能一次性卖断

- 数据库一旦交付到客户手里就可被复制，第二年起没有收入；
- 判据会过期（法规修订、平台规则变更、内部流程调整），**"持续更新"才是订阅的正当理由**；
- 买断模式下你没有动力更新，客户也知道，于是双方都不信这东西能长期用。

### 4.2 三种可售形态

| 形态 | 内容 | 定价 | 适合谁 |
|---|---|---|---|
| **行业模板包** | 某行业 30–80 条判据 + golden set + 报告模板 | 0.8–3 万/年 | 想自己动手的中小团队 |
| **私有判据托管** | 客户判据库 + 版本管理 + 审计链 + 协作 | 2–6 万/年 | 有合规要求的中大型团队 |
| **验收报告服务** | 按次出具可对外/对内的合格性报告 | 200–2000 元/次 | 把交付外包出去的甲方 |

第三种是最容易被忽略、但最像"秤"的生意：甲方不买软件，只买"这批货合不合格"的第三方结论。它单价低但频次高，且天然带信任属性。

### 4.3 铁律：不卖"通用库"

判据不跨行业（见 `06-knowledge.md` 与 D-012）。任何"覆盖全行业 500 条判据"的宣传都会让专业客户立刻判定你不专业。**一次只卖一个行业，且那个行业的判据要深到客户的专家挑不出错。**

## 5. 核心冲突：两条腿的激励方向相反

这是本文最重要的一节。

- 按 **token / 用量** 收钱 → 客户返修 3 次，你收 3 次钱；判定越松，你越赚。
- 按 **验收通过** 收钱 → 交付不合格你不收钱；判定越严（在合理范围内），你越可信。

**同一个客户身上同时存在这两种计价，你的判定就永远洗不清。** 客户会合理地怀疑：你把"响度容差"从 ±1 LUFS 放宽到 ±3 LUFS，是因为这样能少返修、多出片、多计费。一旦这个怀疑成立，判据库的全部价值——中立、可审计、双方都认——当场归零。

### 5.1 四条隔离措施（按成本从低到高）

1. **计价单位与判定结果解耦**：计费只看"是否通过验收"，不看 token 消耗；token 成本单公开，按成本价透传。
2. **判据变更留痕且客户可见**：每次阈值调整都有 who / when / why，客户可查全量变更日志（这本来就是 `06-knowledge.md` 要求的审计能力，此时变成商业信任的凭证）。
3. **承诺条款**：合同中写明"判定逻辑不因计费方式调整"，并给出争议时的复核流程（第三方或客户方专家复核）。
4. **主体或团队隔离**（规模化后再做）：网关业务与判定服务分设主体/团队，损益分开考核，避免销售为了网关用量去压判定。

### 5.2 一个可验证的自检问题

每隔一段时间问自己：**如果把这个客户的计费方式换成"按次固定价"，我会不会调整判据？** 如果答案是"会"，说明冲突已经发生，只是还没被发现。

## 6. 收入结构与年度目标

比例目标（不是预测，是配比约束）：

| 阶段 | 服务 | 订阅 | 网关 | 关键动作 |
|---|---|---|---|---|
| **Y1** | 85% | 5% | 10% | 3 个付费客户，单客户实施 3–8 万；沉淀 3 份模板 |
| **Y2** | 55% | 30% | 15% | 10 家订阅 × 2–3 万 ≈ 20–30 万 ARR；服务只接能沉淀模板的单 |
| **Y3** | 35% | 50% | 15% | 30 家 × 3 万 ≈ 90 万 ARR；服务转为大客户专属 |

量级提醒：**这是一门千万级以内的生意，不是风投故事。** 单行业打透的天花板大致是"可付费客户数 × 年费"，先算清这个数，再决定要不要横向复制第二个行业。

## 7. 计量单位：先定义 `verified_delivery`

如果未来要按结果收费，现在就必须能定义"一次可计费交付"是什么。否则等有客户再补，等于重做 `run` / `verdict` 表。

**定义**：一次 `verified_delivery` = 一次 run 同时满足

1. 全部 `veto` 判据通过（无否决）；
2. `block` 类判据通过率 ≥ 包内 `acceptance.min_pass_rate`；
3. 所有 `gate` 判据已由指定角色签署（含签署人、时间、意见）；
4. 产物已落库且 `artifact_digest` 可复算；
5. 该 run 的知识快照 pin 完整、未发生 drift。

**不足一条即不计费**——这是它与"按次收费"的本质区别：它计的是"合格交付"，不是"跑过一次"。

落点：`run` 表增加 `billable_unit` / `billable_at` / `billing_evidence`（指向 verdict 集合），`verdict` 表已有字段足够支撑，不需要新表。详见 `06-knowledge.md` 的数据模型附录。

## 8. 明确不做的事

| 不做 | 原因 |
|---|---|
| 靠 token 差价做利润中心 | 毛利是时间函数，逐年变薄 |
| 一次性买断判据库 | 可被复制，且失去更新动力 |
| 卖"全行业通用判据库" | 判据不跨行业，专业客户一眼识破 |
| 按"agent 数量"或"席位"定价 | 与产出脱钩，且正在被行业抛弃 |
| 用免费版无限量换数据 | 见 D-012：三处断点，拿到的是最没价值的样本 |
| 为客户定制私有判据结构（改 DSL） | 一旦破例，内核开始长客户形状，S4 压测失效 |

## 9. 风险与待定

| 风险 | 触发信号 | 缓解 |
|---|---|---|
| 服务把团队拖死 | 交付工时 > 70% 人力 | 模板复用率低于 40% 时停止接新单 |
| 客户不接受"判定中立"叙事 | 采购只比价不比判据 | 用"返修率下降"的数据说话，而非功能清单 |
| 网关断供 | 上游条款/区域策略变化 | 多供应商 + 可切换（LiteLLM 就为此存在） |
| 判据被认定为客户资产 | 合同未约定 | 实施前签《判据方法论归属附件》 |
| 按结果计费落地率低 | 客户要求"先按次付，效果后议" | 用混合结构：底价订阅 + 达标返点，而非纯 outcome |
