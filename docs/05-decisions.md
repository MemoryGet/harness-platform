# 关键决策记录与待定问题

格式：ADR 精简版（决策 / 背景 / 结论 / 代价）。

---

## D-001 判据优先，而非流程优先

**背景**：现有平台（Dify / Coze / n8n）解决"流程跑通"，但业务团队仍做不出专业级 agent。专业与业余的差别在判据（什么算合格、什么必须打回），不在流程。

**结论**：产品核心是判据的采集、编译、验收；流程编排只是判据的挂载骨架。

**代价**：销售叙事门槛更高——"帮你画流程"比"帮你沉淀判据"好卖。需要话术与样板客户支撑。

---

## D-002 DSL 是唯一真相，不用画布 JSON

**背景**：若把画布 JSON 当存储真相，UI 就成为内核，换行业必须重写。

**结论**：一切以 YAML DSL 为准，画布只是 DSL 的一个编辑器（S5 甚至先不做画布）。

**代价**：早期没有"所见即所得"的体验，靠 CLI 与 YAML 撑过前 10 周。

---

## D-003 前 10 周不做 UI

**背景**：多数 B 端 agent 平台死在做了一个漂亮的通用画布，业务人员却不用画布、只想改几个参数。

**结论**：S0–S4 只做无头内核；S5 的第一个 UI 是**判据表单**，不是流程编辑器。

**代价**：Demo 不好看，融资/销售演示要靠 CLI 与报告。用 HTML 报告弥补。

---

## D-004 不自研执行壳

**背景**：DeepSeek Harness（MIT 开源、插件化）、Claude Agent SDK、OpenAI Agents SDK 已把工具循环、沙箱、会话恢复做成免费基础设施。

**结论**：执行壳外购/开源接入；自研只限判据引擎、编译器、验收引擎。

**代价**：多一层依赖；需要在 IR 层做抽象，保证编排器可替换。

---

## D-005 IR 自持，编排器可换

**背景**：LangGraph 等编排框架变化快，直接绑死会有迁移痛。

**结论**：自定义 IR（JSON）作为编译产物，向下可生成 LangGraph 图、DSH 配置或纯 Python 函数链。S2 先用自写拓扑排序，不引入重依赖。

**代价**：需要自己写拓扑排序与状态机（约 500 行），换长期可替换性。

---

## D-006 采集与判定分离（`fn` vs `assert`）

**背景**：业务人员要能改阈值，但改不了采集代码。

**结论**：`rule` 类检查器拆成"采集函数 `fn`"（工程师维护，注册表）与"声明式断言 `assert`"（业务人员改）。S5 表单只暴露 `assert`。

**代价**：采集函数需要覆盖足够多的场景，否则业务人员会遇到"没有合适的 fn 可用"。

---

## D-007 四槽位（input / process / quality / veto）

**背景**：需要一个最小完备的槽位集，既能覆盖专家访谈的提问维度，又能对应不同的运行时行为。

**结论**：固定四槽位。访谈四问 ↔ 四槽位一一对应。

**代价**：若某行业有"第五类"判据（如成本约束），需强行归入四槽之一。目前归入 `quality`。

---

## D-008 `judge` 不得进入 `veto` 槽位

**背景**：模型评审具有概率性，不适合承担否决权。

**结论**：`veto` 只能由 `rule`（确定性）或 `gate`（人）承担。

**代价**：某些"只能靠模型判断的严重风险"需要退化为 `block` + 人工兜底。

---

## D-009 判据包发布后不可变

**背景**：可审计要求"当时用的是哪版判据"必须可回溯。

**结论**：`(tenant_id, pack_id, version)` 组合唯一且不可修改；改判据 = 发新版本。运行时记录 pack 快照 checksum。

**代价**：判据会产生较多版本，需要 UI 做版本管理与清理。

---

## D-010 第一天就做多租户

**背景**：租户字段后加等于重构全部表与查询。

**结论**：`tenant_id` 出现在所有业务表首字段并参与主键，即便单客户阶段。

**代价**：本地开发略繁琐，用默认租户常量兜底。

---

## D-009 知识库是依据层，不是 RAG 插件

**背景**：常见做法是接一个向量库、检索 top-k 塞进 prompt。这条路径在判定链路上会带来三个后果：同一输入不同结论（不可复现）、judge 说不清出处（不可追溯）、规范改版后新旧版本并存被误引（不可失效）。在合规场景下第三条不是 bug，是事故。

**结论**：知识库只承担三种用途——判据依据 `basis`、检查依据 `grounding`、生成上下文 `retrieval`；只有前两种参与判定，且判定链路只允许按 `item_id` / `path` 精确检索。判据依据在编译期绑定为 `item_id` + 快照，运行时零检索；`judge` 输出必须带引用，由校验器做四项闭环验证（条目存在 / 当前生效 / 原文子串 / 权威级足够）。详见 `06-knowledge.md`。

**代价**：知识入库成本上升——要结构化到条款级、维护生效期与替代链、每次规范更新都要重建快照。以及业务专家必须为每条硬判据交代出处。后者既是成本也是价值：填不出依据的判据，本来就不该拥有否决权。

---

## D-010 MCP 是接入方式，不是架构层

**背景**：用户会自带知识库——可能是文档目录，也可能是 Notion / 语雀 / 自建系统通过 MCP 暴露。常见做法是把 MCP 直接挂给 agent（执行壳），或让内核运行时直连。两条都不成立：壳直连则判定失去依据控制，内核直连则判定不可复现（MCP 无快照语义、只返回片段、延迟不可控）。

**结论**：接入收敛在平台侧的**连接器注册表**，向下分两条通道——①入库通道（唯一可写）通过 `Provider.sync()` 拉全文物化成快照，内核判定只读本地快照；②生成通道通过 `Tool Gateway` 给执行壳只读工具，并注入当前 run 的 pin。内核的 `Provider` 接口不暴露 `search`；壳的工具白名单不含任何写能力。详见 `07-knowledge-integration.md`。

**代价**：需要维护锚点映射表（外部 id ↔ 稳定 item_id）与增量同步策略，接一个新源不是"配个 URL"那么轻。以及远端内容变化变成显式事件（发布新快照 / 阻断发布），需要产品化"依据升级"流程，而不是静默生效。

**范围说明**：本决策只覆盖**入库通道 + 内核判定**。执行壳如何接入知识库（是否接 MCP、如何与快照保持一致）**暂缓**，推迟到 S2 之后再定，见 Q14 与 `07-knowledge-integration.md` §8。当前壳侧不接知识库 MCP。

---

## D-011 复合任务用契约式组合，不做嵌套编排

**背景**：真实业务常由多个子任务组合而成（一个上市内容包 = 视频 + 图文 + 法务审查），最后汇总交付。直接的做法是允许 workflow 里嵌套 workflow，但那会逐步长成 BPMN：子图、跨层变量、跨层条件、跨层异常，最后没有一个业务人员能读懂自己的流程，内核也被拖进通用编排的泥潭。

**结论**：父包只声明四件事——子任务清单（引用别的判据包）、产物槽位、父对子的验收门槛、汇总判据。子包对父包是黑盒，**父层不描述子层内部任何 step**。子任务是独立 run（`parent_run_id` 关联），不是 step；缓存键为 `pack@version + inputs + knowledge_pin_set`，因此改一条子任务判据只需重跑那个子 run。嵌套深度硬限两层。失败传播中"子 veto → 父 veto"强制生效、不可配置。详见 `08-composition.md`。

**代价**：跨层信息传递必须显式（父包 `inputs` 映射），不能靠子 agent 自己"看一眼"；编译期要做输入契约匹配（V-COMP-03），这要求子包显式声明必填输入（见 Q15）。另外父子两级 gate 可能重复审批，需要编译期去重告警。

## 已知风险

| 风险 | 触发信号 | 缓解 |
|---|---|---|
| 四槽位不足以覆盖某行业 | S4 压测时某行业反复要加第五槽 | 允许 `slots.extra` 扩展位，但不进内核 |
| 采集函数（`fn`）永远不够用 | 业务人员频繁报"没有可用 fn" | 提供"手写断言 + 表达式"兜底，允许对已采集证据做任意组合 |
| 业务人员表达不出判据 | S0 访谈低于 8 条 | 换行业，或改用"看历史返修记录反推判据" |
| 判据包版本爆炸 | 单包周版本 > 5 | 合批发布 + 草稿态 |
| 模型评审抖动导致门禁时过时不过 | 同一 pack 两次 eval 差异 > 5% | `samples` 提到 5，用中位数；固定 temp=0 |
