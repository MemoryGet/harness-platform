# 外部知识库接入（MCP / 文档 / 对象存储）

> 状态：草案 v0.1。承接 [06-knowledge.md](06-knowledge.md)——06 定义"知识怎么被判定使用"，本文定义"外部知识怎么进来、由谁读、由谁写"。
> 核心问题：用户自带知识库（文档目录，或 Notion / 语雀 / 自建系统通过 MCP 暴露），这个 MCP 应该由执行壳用，还是由内核用？

## 1. 直答

**MCP 不是一个层，是一种接入方式**——和 HTTP 一样。所以"MCP 挂在哪一层"这个问题本身没有答案，正确的问法是三个：

| 问题 | 答案 |
|---|---|
| 谁读它做**判定**？ | 内核，但**不直连**，读的是物化后的本地快照 |
| 谁读它做**生成**？ | 执行壳，作为只读工具直连 |
| 谁**写**它？ | 只有平台侧的入库通道，壳永远没有写权限 |

一句话：**两层都要用，但用法不同、通道不同、权限不同，且在注册表层收口。**

## 2. 接入拓扑

```
外部源（MCP 知识库 / 文档目录 / 对象存储）
        │
   ┌────▼─────────────────────────────────┐
   │ 连接器注册表（平台层）                │  凭证、租户绑定、权限范围、能力探测
   └────┬───────────────────────┬─────────┘
        │                       │
   ┌────▼──────────────┐   ┌────▼──────────────┐
   │ 入库通道（可写）   │   │ 生成通道（只读）   │
   │ sync → 物化 → 快照 │   │ Tool Gateway       │
   └────┬──────────────┘   └────┬──────────────┘
        │                       │
   ┌────▼──────────────┐   ┌────▼──────────────┐
   │ 内核 Provider      │   │ 执行壳 agent       │
   │ 读本地快照，判定   │   │ 实时检索，仅参考   │
   └───────────────────┘   └───────────────────┘
```

三个判断：

1. **连接器注册表不属于内核，也不属于壳。** 它管的是"用哪个端点、谁的凭证、能读哪个范围"——这是部署与授权问题，跟判据无关。放进内核会让内核依赖具体厂商，放进壳会让 agent 拿到凭证（最危险）。
2. **入库通道是唯一可写路径。** MCP 的 `create` / `update` / `append` 只在这里开启，且只对同步 worker 身份开放。
3. **执行壳只有读。** 这是安全红线，见 §9。
4. **生成通道暂缓。** 壳侧的知识接入整体推迟到 S2 之后再决策（§8 的三个方案都未定）。在那之前，壳侧不接知识库 MCP。

## 3. 为什么判定不能运行时直连 MCP

| 缺陷 | 后果 |
|---|---|
| MCP 协议**没有快照/版本语义** | 只能回答"现在是什么"，无法回答"当时依据的是哪一版"，判定不可复现 |
| `search` 是**模糊召回** | `basis` 需要按 `path` 精确到条款级，模糊召回给不出稳定锚点 |
| 多数实现只返回**片段（snippet）** | `quote` 的原文子串校验无法执行，引用闭环失效 |
| **延迟、限流、可用性**都在对方手里 | 一次判定几十条判据，每条一次远端调用；对方抖动 → 你的验收全线失败 |

还有一条更隐蔽的：**远端内容会在你不知情时改变**。用户今天更新了 SOP，你的历史判定就与现在的依据对不上了，而你没有任何机制能发现——因为 MCP 不告诉你"变了什么"。

结论：**MCP 是入库通道，不是运行时通道。**

## 4. sync-on-ingest，read-local

```
① 同步      入库 worker 按 scope 拉取条目（含全文，非片段）
② 物化      落 knowledge_items：稳定 id、path、body、checksum、生效期
③ 校验      同源 path 唯一、替代链单调、区间不重叠（V-KB-09/10）
④ 冻结      生成新快照，status=active；旧快照 retired 但不删
⑤ 判定      内核只读本地快照，零远端依赖
```

远端变化不会"漂移"进判定，而是变成**新快照**。包仍然 `pin_at_publish` 指向旧快照，直到有人显式做一次"依据升级"——这次升级会产生 diff（哪些条款变了、哪些判据受影响），并且可以只对 10% 任务灰度生效。

这就是"用户的知识库一直在变"和"判定必须可复现"之间的唯一解法：**变化是显式事件，不是隐式副作用。**

## 5. Provider 接口：故意不暴露 `search`

```python
class KnowledgeProvider(Protocol):
    def describe(self) -> SourceDescriptor:
        """能力探测：是否支持增量、是否给稳定 id、单次拉取上限"""

    def sync(self, since: datetime | None, scope: SourceScope) -> SyncResult:
        """入库通道。返回新增/变更/删除的条目清单与 checksum"""

    def resolve(self, ref: ItemRef) -> Item:
        """按 item_id 或 path 精确取。判定链路只允许这条"""
```

注意接口里**没有 `search()`**。不是遗漏，是设计：从类型层面让"判定链路调用模糊检索"写不出来。需要模糊检索的是执行壳，它走 MCP 原生工具，不经过这个接口。

这带来了实现的三种 Provider，对内核完全等价：

| 实现 | 场景 | 特点 |
|---|---|---|
| `FilesystemProvider` | 用户上传的文档目录 | 直接读，checksum 即文件哈希 |
| `McpProvider` | Notion / 语雀 / 自建知识库 | 需锚点映射与全文抓取，见 §7 |
| `ObjectStorageProvider` | S3 / OSS / 网盘 | 增量靠 mtime + etag |

**用户换知识库厂商时，内核代码一行不改**——这是把 MCP 关在适配器内部的直接收益。

## 6. DSL 声明

```yaml
knowledge:
  sources:
    - id: kb-customer-sop
      name: 客户内部 SOP（Notion）
      source_type: internal_sop
      authority: internal_mandatory
      pin_policy: pin_at_publish
      required: true
      provider:
        type: mcp                 # mcp | filesystem | object_storage
        server: notion-kb         # 连接器注册表里的名字，不是 URL
        scope: "workspace:acme/space:sop"
        fetch_full_text: true     # 必须拉全文，否则 quote 校验不可用
      sync:
        mode: scheduled           # manual | scheduled | on_demand
        cron: "0 3 * * *"
        on_change: new_snapshot   # new_snapshot | block_publish
```

三条约束：

1. **YAML 里不写凭证**，只写 `server` 名字。凭证在连接器注册表里按租户加密存储——判据包可能被导出、被分享、被提交到 git，任何塞进 YAML 的密钥都会泄漏。
2. **`fetch_full_text` 必须为 true** 才能被 `basis` 引用。只索引片段（index_only）的源只能服务生成层，等同 `follow_latest`，V-KB-04 会拦住它被引用。
3. **`on_change: new_snapshot`** 是默认策略：远端变了就产新快照，不自动改包。若客户要求"规范一改全线生效"，用 `block_publish`——先阻断发布，等人确认升级。

## 7. MCP 接入的三个实际坑

这三个坑不写清楚，第一次接入必然返工。

### 7.1 锚点映射：从 page_id 到稳定 path

MCP 通常给的是 `page_id` + `block_id`，而 `basis.path` 需要人类可读且稳定的定位（`内部审查指引/3.2 责任限额`）。两个问题：

- **标题会变**：SOP 改名后 path 变了，所有 `basis` 失效 → 所以内核的 `item_id` 必须与 path 解耦，path 只作展示与人工定位，绑定用 `item_id`。
- **page_id 不稳定**：部分产品在复制/迁移时会生成新 id → 需要维护一张 `external_ref_map(source_id, external_id, item_id)` 映射表，同步时比对，识别"移动/改名"而非"删除+新增"。

没有这张映射表，每次同步都会产生大量假删除，历史 `basis` 全部断链。

### 7.2 snippet ≠ 原文

`search` 返回的片段常被服务端做过截断、加省略号、或按块切分。用片段做 `quote` 校验，通过率会低到无法使用，而且失败原因看起来像"模型幻觉"，实际是数据源问题。

规则：**`search` 只用于发现，`fetch` 才用于校验。** 同步时必须 `fetch` 完整条目正文（或按 block 拼接完整正文）落库。

### 7.3 增量同步与 checksum

- 只按 `updated_at` 增量拉取，会漏掉"静默改动"（有的系统不改时间戳）。
- 因此：**条目 checksum 必须覆盖全文**，每次同步对已拉取条目做一次校验；每周做一次全量比对兜底。
- 删除必须显式处理：源里删掉的条目，快照里标 `deleted_at` 而不是真删——否则历史判定会引用到"已经不存在的条目"，审计断链。

## 8. 壳体直连的一致性问题（暂缓，S2 后再定）

> **本节未定，不构成决策。** 执行壳侧的知识接入整体推迟——当前的实现范围只有"入库通道 + 内核判定"这条链路，壳侧在此之前不接知识库 MCP。下面三个方案先留档，等内核算路跑通、真正需要生成侧检索时再选。

同一份知识被两条通道读到不同版本，会产生一个隐蔽矛盾：**壳写稿时用了新版规范，内核判定时按旧版规范**。产出与标准不一致，评审人看到的是"按新规写的、按旧规被打回"。

三种处理，按强度排序：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. pin 透传**（推荐） | Tool Gateway 调 MCP 时注入当前 run 的 pin 集合，让壳也只能看到锁定快照 | 需要 MCP 支持过滤条件或版本参数；不支持则退化到 B |
| **B. 双读 + 标注** | 壳读实时，但产出里的引用不参与判定；报告标 `knowledge_drift` | 判定与产出可能不一致，需人工看标注 |
| **C. 只读快照副本** | 给壳挂一个"快照只读 MCP"，它读的其实是内核物化后的数据 | 要多维护一个 MCP 端点，但一致性最好 |

对合规类场景（法务、医疗、金融）建议直接上 C：让壳读的也是物化副本，物理上不可能读到未冻结版本。

## 9. 权限模型（三层，缺一不可）

| 层 | 控制什么 | 典型配置 |
|---|---|---|
| **租户层** | 哪个租户能接哪个源 | 连接器绑定 `(tenant_id, server)` |
| **连接器层** | 该连接能读写什么 | 只读 scope；写能力只授给 sync worker 身份 |
| **判据包层** | 哪条判据能引哪些源 | `knowledge.sources` + `grounding.sources` 白名单 |

**最关键的一条：执行壳的工具白名单里，知识库 MCP 只有 `search` / `fetch` / `list`。**

理由不是"怕它乱改文档"，而是：**如果 agent 能写知识库，它就能修改自己的判据依据，让验收通过。** 这等于让考生改考卷。任何"agent 自动补充知识库"的功能，都必须走"生成候选条目 → 人工审核 → 入库"的人工闸门，不能直连写入。

同一条原则也适用于平台自身：**入库通道写的是快照，不是源**。平台永远不往用户的知识库回写内容（除非用户显式要求双向同步，那是另一个产品功能，且必须与判定链路隔离）。

## 10. 实时需求：那不是知识库，是 evidence

经常出现的需求："我们的价目表每天变，判定要按最新价"。

这不能靠"知识库实时化"解决——**依据必须可钉版本**，这是判定可复现的前提。正确处理是换一种载荷：

| 需求 | 不是 | 而是 |
|---|---|---|
| 按最新价目判定 | `basis` 指向知识库 | `evidence` 由 `tool.price_lookup` 实时采集，判据断言 evidence 字段 |
| 按当前库存决定能否接单 | 知识库检索 | 工具调用，结果进 `evidence`，随 run 冻结 |
| 按最新法条判定 | 知识库实时同步 | 法条走知识库（低频、强版本），同步频率提到每日即可 |

判据只认 `evidence` 和 `basis` 两种输入，前者可实时、后者必冻结。这条界线一旦模糊，整个可复现性就没了。

## 11. 落地顺序

| 阶段 | 做什么 | 不做 |
|---|---|---|
| **S1** | `FilesystemProvider` + `Provider` 接口 + 物化与 V-KB-09/10 | 不接 MCP（先把本地链路跑通，接口才不会被厂商细节污染） |
| **S2** | `McpProvider`：锚点映射表、全文 fetch、增量同步 | 不做连接器管理 UI（配置文件即可） |
| **S3** | 引用闭环 + `knowledge_drift` 标注 + 覆盖率门禁 | 不做自动依据升级（先人工确认） |
| **S6** | 连接器注册表 UI、租户授权流程、快照升级 diff 视图 | 不做双向同步 |

**先本地后 MCP** 的理由：MCP 接入会引入大量厂商特性（分页、限流、id 不稳定），如果 `Provider` 接口是在接 MCP 的过程中长出来的，它一定会长得像某个具体产品。先用文件系统跑通，接口只表达"判定需要什么"，再接 MCP 做适配——这才是适配器模式的正确顺序。

上表**不含壳侧接入**：生成通道的落地顺序要等 §8 决策后再排，不在当前范围内。

## 12. 待定问题

1. **MCP 不支持 pin 过滤时怎么办？** 退化到 §8 的 B 方案（双读 + drift 标注），还是强制要求用户换源？建议：合规场景强制 C（快照只读副本），效率场景允许 B。
2. **锚点映射表归谁维护？** 平台自动推断（标题相似度 + 位置）还是要求用户手工确认？建议：自动推断 + 变更超过阈值时要求确认。
3. **一个判据包同时引多个 MCP 源，快照时间不同步怎么办？** 建议：编译期记录各源快照时间，超过 24 小时差异时告警，不阻断。
4. **用户源里的权限（谁能看哪个页面）要不要继承？** 若继承，同一份判据对不同用户会得出不同结论——建议不继承，入库时按服务账号的可见范围全量物化，靠租户级隔离而非文档级隔离。
